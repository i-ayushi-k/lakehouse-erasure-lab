# Data Card: Lakehouse Erasure Lab

## Dataset identity

**Name:** Lakehouse Erasure Lab synthetic benchmark dataset

**Type:** Synthetic, locally generated structured data

**Primary purpose:** Test a user-erasure workflow across simulated analytical storage layers and measure local execution latency.

## Data origin and composition

Records are generated by the project code for testing. The benchmark exercises datasets with 100, 1,000, 5,000, and 10,000 synthetic records.

The pipeline includes:

- A source representation.
- Derived records.
- A feature-like table.
- A vector-like table.
- A Parquet historical copy.
- A local Apache Iceberg pipeline table with Parquet data files and snapshot metadata.

The exact schema and generation logic are defined in `src/erasure/pipeline.py` and `src/erasure/iceberg_store.py`. The benchmark driver is in `scripts/benchmark.py`.

## Personal data and privacy

The intended benchmark uses synthetic identifiers and synthetic values, not collected real-world personal data. User identifiers are used to select records for deletion testing.

Before reusing or extending the project, inspect any changed data-generation code and confirm that real user data, credentials, or private records have not been introduced.

## Intended use

- Educational demonstrations of deletion propagation.
- Local regression tests for the implemented deletion logic.
- Basic comparisons of deletion latency across synthetic dataset sizes.
- Demonstrations of local Apache Iceberg table operations and snapshot expiration.
- Discussion of historical data, derived records, and verification gaps.

## Out-of-scope use

The dataset and measurements must not be used to claim:

- Production lakehouse performance or scalability.
- Complete erasure from a distributed data platform.
- Verified deletion from external feature stores or vector databases.
- Physical erasure from backups or replicas.
- Compliance with GDPR, India's DPDP Act, or any other legal framework.

## Known limitations and biases

- The data is synthetic and does not represent real user distributions.
- The benchmark is small and local; hardware, Python version, cache state, and system load affect results.
- Only three repetitions were recorded for each original benchmark size.
- The measured latency should not be generalized to concurrent or distributed workloads.
- The vector and feature components are DuckDB table simulations.
- The historical Parquet-copy mechanism removes registered local Parquet files.
- The Iceberg integration separately demonstrates current-state deletion, snapshot expiration, and local orphan-file cleanup.
- DuckDB and Iceberg do not share a distributed transaction. A failure in one system may not roll back a successful operation in the other.
- Verification covers the locations and conditions implemented in the code, not every possible copy of a record.
- The Iceberg file cleanup is intended for the dedicated local demonstration table, not production storage.

## Benchmark interpretation

Previously recorded benchmark measurements represent the original local DuckDB prototype. They should not automatically be presented as performance measurements of the integrated DuckDB and Iceberg implementation.

Regenerate benchmark outputs using the current implementation before making new performance claims.

## Maintenance

When the schema, generator, deletion logic, storage integration, or benchmark methodology changes:

1. Update this data card.
2. Update the architecture documentation and technical report.
3. Regenerate benchmark outputs when the methodology or implementation changes.
4. Rerun the automated test suite.
5. Review verification results and document any newly identified limitations.
